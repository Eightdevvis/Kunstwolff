# Mehrsprachigkeit (i18n-Fundament, Phase 1)

Die Website kann fremdsprachige Seiten ausliefern, **ohne** dass sich am deutschen
Verhalten irgendetwas ändert. Das ist der Kern des Entwurfs und der Grund, warum das
Fundament so unauffällig ist: Deutsch (`de`) bleibt der Default und bleibt
**unpräfigiert** (`/belgique/`), Fremdsprachen bekommen ein URL-Präfix
(`/fr/belgique/`).

Aktueller Beweis-Umfang: **eine** Sprache (`fr`), **eine** Seite (`/fr/belgique/`).

## Die eine Quelle: `src/i18n/config.ts`

| Export | Zweck |
| :-- | :-- |
| `DEFAULT_LOCALE` | `'de'` – unpräfigiert |
| `LOCALES` | `['de', 'fr']` (`'nl'` steht als Kommentar für Phase 2 bereit) |
| `LOCALE_META` | Label, `hreflang` und `htmlLang` je Locale. ⚠️ Das Feld `hreflang` (`fr` → `'fr-BE'`, Belgien statt Frankreich) wird **derzeit von niemandem gelesen**: `Layout.astro:69` gibt `hreflang={a.locale}` aus, also schlicht `fr`. Benutzt werden nur `label` und `htmlLang` |
| `PREFIXED_LOCALES` | alle außer `de` |
| `localizePath(locale, slug)` | `de` → `/<slug>/`, sonst `/<locale>/<slug>/`. **Leerer Slug = Sprachwurzel** (`/` bzw. `/fr/`) – ohne diesen Fall entstand `//`, weil die Vorlage den Schrägstrich auf beiden Seiten setzte. Aufgefallen im Breadcrumb-Schema der FR-Seite („Accueil" zeigte auf `https://kunstwolff.de//`): im Browser folgenlos, in strukturierten Daten eine Adresse, die es nicht gibt |
| `localeContentRoot(locale)` | `de` → `public/`, sonst `public/i18n/<locale>/` |
| `resolveLocalizedFile` / `resolveLocalizedDir` | Overlay-Auflösung mit Rückfall aufs deutsche Original |
| `getTranslatedLandingSlugs(locale)` | liest `public/i18n/<locale>/landings.json` – **der Phase-2-Schalter** |
| `getAvailableLocalesForSlug(slug)` | welche Sprachen es zu einem Slug gibt (für den Umschalter) |

## Content-Overlay statt Übersetzungsdateien

Übersetzte Inhalte liegen unter `public/i18n/<locale>/` und **spiegeln die bestehende
`public/`-Struktur**. Es gibt keine Schlüssel-Wert-Tabellen und keinen zweiten
Content-Typ – dieselben Loader lesen dieselben Formate, nur unter einer anderen Wurzel.

```
public/i18n/fr/
├── landings.json                 # welche Slugs es auf FR gibt
├── site-texts/content.json
├── why/default.json
├── why/belgique.json
└── faq/belgique/{branding,buchung,kosten}.md
```

**Fehlt eine Overlay-Datei, greift automatisch das deutsche Original.** Eine
teilübersetzte Seite ist deshalb nie leer, sondern gemischt – und die deutschen Pfade
bleiben unberührt. Das ist die Eigenschaft, die den ganzen Umbau risikoarm macht.

Locale-fähige Loader: `faq.ts`, `why.ts`, `siteTexts.ts` (jeweils dritter bzw. erster
Parameter `locale`). Alle anderen Loader kennen keine Locale und liefern immer Deutsch.

## Route und Umschalter

- `src/pages/fr/[landing].astro` baut die FR-Seiten aus `getTranslatedLandingSlugs('fr')`.
  Sie liest denselben Sektions-Stack aus `components.json` (Kategorie `landing`),
  filtert ihn aber zusätzlich über `LOCALE_READY_SECTIONS` und benutzt bewusst
  `getSectionOrder` statt `resolveSectionOrder` – Details und die Liste der dort
  unterdrückten Sektionen in `komponenten-stack.md`.
- `src/components/LangSwitcher.astro` rendert **nichts**, solange keine echten
  Alternativen übergeben werden (`alternates.length > 1`). Auf allen rein deutschen
  Seiten ist das HTML damit unverändert – der Umschalter kostet dort kein einziges Byte.
- `Layout.astro` nimmt `lang` als Prop (Default `"de"`) und gibt bei mehreren
  Sprachvarianten `<link rel="alternate" hreflang=…>` aus (`seo.md`).

## Eine neue Sprache aufnehmen

1. Locale in `LOCALES` und `LOCALE_META` eintragen.
2. `public/i18n/<locale>/landings.json` mit den übersetzten Slugs anlegen.
3. Overlay-Inhalte anlegen – nur die, die wirklich übersetzt sind.
4. Route anlegen (`src/pages/<locale>/[landing].astro`, analog zu `fr`).

Schritt 4 ist der einzige Code-Schritt; die Route liest die Registry, sonst ist nichts
anzupassen.

## Was noch fehlt (Phase 2)

- Das Admin-Tool kennt die Overlay-Pfade **nicht** – FR-Inhalte werden von Hand
  gepflegt (`admin-tool.md` listet `public/i18n/` nicht als Schreibpfad).
- Der Umschalter sitzt noch nicht in der Navigation (`Header.astro`), sondern
  als sichtbarer Beweis im Layout.
- `/fr/belgique/` steht in der Sitemap, aber `hreflang` steht nur im `<head>`, nicht
  als `xhtml:link` in der Sitemap – und der ausgegebene Wert ist `fr`, nicht das in
  `LOCALE_META` hinterlegte `fr-BE`.
